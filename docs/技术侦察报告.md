## 假设 3：clip-path polygon 字符串插值 —— 成立（有严格前置条件）

### 证据

1. **GSAP 官方论坛版主明确说明插值机制**
   - URL：https://gsap.com/community/forums/topic/35519-clip-path-not-animated-smoothly/ （Cassie，2023-01-27 标记为 Solution）
   - 原文：「that's because it's just animating a complex string which involves isolating the numbers in each string (the beginning and ending one), and then interpolating those.」
   - 原文：「So the first number in the starting string gets matched with the first number in the ending string, and so on.」
   - 原文：「If you make them all percentages it works fine. It's hard for GSAP to animate between 0 and 100% as they're different units.」
   - 修正写法示例（全百分比）：`polygon(100% 100%, 0% 100%, 0% 100%, 100% 100%)` → `polygon(100% 100%, 0% 100%, 0% 0%, 100% 0%)`

2. **同构字符串约束**
   - URL：https://gsap.com/community/forums/topic/42313-clip-path-animation-inset-vs-polygon/ （mvaneijgen 标记为 Solved，2024-09-12）
   - 版主原文：「When animating between complex strings it is important that you animating between the same type of strings, in this case you'll need to prefix your 0 with px eg inset(0% 0% round 0) becomes inset(0% 0% round 0px) because your initial state also used a px in the string.」
   - Rodrigo 原文：「The main issue is the fact that the browser reports fewer values than the ones GSAP uses.」——`getComputedStyle` 会把 `inset(4% 4% round 40px)` 压缩成 `inset(4% round 40px)`，GSAP 以为有 3 个值，于是给缺失值补 `0`，造成跳动。

### 成立的前置条件（必须写进方案 19.2）

1. 起点和终点必须是同一种函数：`polygon()` 对 `polygon()`，不能跨类型。
2. 点数完全一致：4 点只能补间到 4 点，不能 4→5。
3. 单位完全一致：全用 `%` 或全用 `px`，**禁止混用**（尤其 `0` 与 `100%` 混用）。
4. 数值顺序一一对应，不要依赖浏览器 computed style 的归一化结果。
5. 用 `gsap.set()` 或 `gsap.fromTo()` **显式同时指定两端字符串**，不要只写终点、依赖 CSS 初始值。

### 对方案的影响

- 「19.2 裁切方案失效」的后果**不成立**，但方案必须按上述契约改写：所有 `clip-path: polygon()` 裁切动效统一用**全百分比、固定点数、fromTo 显式两端**。
- 若裁切需要变点数（例如 4 点→6 点），GSAP 原生插值不可用，需改为：拆成两条同点数时间线交叉过渡，或改用 mask/transform 方案。
- 本项属于「文档+论坛确认，但具体模板仍需实机 smoke test」，建议为裁切动效加一条截图回归用例。

## 假设 4：headless 确定性逐帧 seek —— 成立（必须遵守整套契约）

### 证据

1. **HyperFrames 官方确定性文档**
   - URL：https://hyperframes.heygen.com/concepts/determinism （最后修改 `2026-11-12T18:11:13Z`）
   - 核心保证原文：「Same input, identical output. Every time.」
   - 帧时钟原文：「The engine works out the time with integer math: `time = floor(frame) / fps`. Real time is never consulted.」
   - GSAP 约束原文：「All GSAP timelines are paused and seeked, never played.」
   - 捕获原文：「Chrome's `HeadlessExperimental.beginFrame` grabs the pixels in one atomic operation. No half-painted frames.」
   - 禁止项原文：「No wall clock. No `Date.now()`, no `requestAnimationFrame`, no system timers.」「No unseeded randomness.」「No fetching mid-render. Every asset loads before the first frame.」「Fixed output size.」
   - 环境原文：「Fonts and Chrome versions differ between computers... Render in Docker when you need exact reproducibility.」
   - 例外：「Motion blur is the exception.」——运动模糊会破坏逐帧一致性，需谨慎。

2. **HeyGen 一手工程经验（证明路线已被生产验证，也列出全部坑）**
   - URL：https://www.heygen.com/research/html-to-video （James Russo，2026-06-22）
   - 坑 1：`Page.captureScreenshot` 与渲染竞态——截图可能在字体未加载、布局未完成、GSAP 最终样式未提交、GPU 未完成绘制时返回。解法：Linux Docker 中用 `chrome-headless-shell` + CDP `HeadlessExperimental.beginFrame`，一次调用完成 layout→paint→composite→screenshot。
   - 坑 2：BeginFrame 模式下页面事件循环被冻结，`document.fonts.ready` 永远挂住。解法：warmup loop——加载期间每 33ms 发一次 `beginFrame(noDisplayUpdates: true)` 推进事件循环；把 Google Fonts 改为本地 base64 字体。
   - 坑 3：浏览器与 GSAP 各自有时钟。解法：「Seek, don't play」——composition 暴露 `window.__hf = { duration, seek(t) }`，逐帧调用 `seek(i/fps)`；GSAP 用 `timeline.pause() + timeline.totalTime(t, false)`。
   - 坑 4：`page.waitForFunction` 底层用 rAF 轮询，BeginFrame 模式下挂起并最终 timeout。解法：Node 侧 `page.evaluate()` + `setTimeout()` 手动轮询 ready；渲染加固定 flags（`--deterministic-mode`、`--enable-begin-frame-control`、`--run-all-compositor-stages-before-draw`、`--disable-threaded-animation` 等）。
   - 额外约束：时间量化 `Math.round(time * fps) / fps`；preview 与 render 共用同一 runtime bundle 并以 sha256 校验；`<video>` 先用 FFmpeg 预解码成编号 JPEG 帧再渲染；禁止 composition 内 `Date.now()`、未 seed 的 `Math.random()`、render 时网络请求。
   - 明确限制：**最强确定性路径依赖 Linux + chrome-headless-shell + Docker/CI**；macOS/Windows 只能走 `Page.captureScreenshot` + 启发式等待，稳定性较低。

### 对方案的影响

- 「整个渲染管线失效」的后果**不成立**：`paused timeline + t → seek` 正是业界已验证的确定性渲染范式，本项目「所有层挂单条 GSAP 时间线、`MASTER.time(t, false)` 唯一驱动、零 rAF」的设计与该范式一致。
- 但必须补齐以下工程约束，否则会踩上述坑：
  1. **时间量化**：所有 `t` 先按 `round(t * fps) / fps` 量化，避免浮点误差产生相邻像素差异。
  2. **ready gate**：截图前显式等待字体与素材就绪；不要用依赖 rAF 的 `waitForFunction`。
  3. **捕获方式**：优先 `HeadlessExperimental.beginFrame` 原子截图；Docker 固定 Chromium/字体/FFmpeg 版本。
  4. **禁用隐式时间源**：`Date.now()`、未 seed `Math.random()`、render 中 fetch、rAF 自驱动一律禁止（与 `CODING_STANDARDS.md` 一致）。
  5. **媒体预解码**：视频素材预抽帧为编号图片，渲染时不让浏览器播放 `<video>`。
  6. **`.time()` 与 `.totalTime()` 的差异（需规范明确）**：方案写 `MASTER.time(t, false)`，HyperFrames 实践用 `timeline.totalTime(t, false)`。当时间线无 `repeat`/`yoyo`/子时间线偏移时两者等价；一旦引入 repeat 或嵌套，`.time()` 会忽略重复周期。建议：规范中明确**禁用 repeat/yoyo**，或统一改用 `.totalTime(t, false)`，二者取一，避免回归测试不过。
  7. **运动模糊**：若启用 motion blur，确定性保证失效，需关闭或单独验证。

## 补充侦察：后端落地决策（2026-11-17 二轮）

### 前提澄清

team-lead 补充要求假设「HyperFrames 开源 CLI 不存在或不可用」。**该前提经一手证据证伪**：官方仓库存在、LICENSE 为 Apache 2.0、FAQ 确认 CLI 开源且本地渲染免账号（见假设 1）。因此下面的「备选方案」不是待激活的 PLAN B，而是用于证明首选决策正确的对照。**决策不变：v1 后端用 HyperFrames。**

### 明确表态（可直接指导落地）

1. **主路径**：v1 渲染层直接对接 `npx hyperframes` CLI / `@hyperframes/engine`，不要自研浏览器渲染管线。理由：HyperFrames 已把 beginFrame 原子截图、字体 warmup、虚拟时钟、视频预解码、Docker 环境固定这些「确定性渲染最难且最容易踩坑的部分」全部实现并文档化；自研等于重做一遍 HeyGen 工程博客里列出的四大坑。
2. **工程环境**：本地开发支持 Windows（官方 Quickstart 明确含 Windows on Arm；URL https://hyperframes.heygen.com/quickstart ），但**严格逐像素可复现必须在 Linux Docker**（官方确定性文档原话：「Render in Docker when you need exact reproducibility」，命令 `npx hyperframes render --docker --output output.mp4`）。这与本项目 win32 工作区不冲突：开发在 Windows、CI/确定性回归在 Docker。
3. **接入契约**：渲染层只需保证 composition 暴露可 seek 的时间线（`paused` + `seek(t)`），把 `MASTER.time(t,false)` 接到其 frame adapter；`t` 先做 `round(t*fps)/fps` 量化。渲染层不碰编排层时间线语义。
4. **验收门槛**：在 Linux Docker 中对同一 composition 同一 `t` 渲染两次，截图 hash 必须一致（`CODING_STANDARDS.md` 第 5 节已有要求）。这条通过，才认为后端可用；不通过则优先排查字体/隐式时间源/媒体预解码，而不是换后端。

### 如果 HyperFrames 真的不可用（决策树，按优先级）

| 顺位 | 方案 | 许可 | 阈值 / 成本（官方证据） | 成熟度判断 |
|---|---|---|---|---|
| 1 | **Revideo** | MIT（官方站 https://re.video/ 自述「fully open source and MIT licensed」） | 无门槛，可商用 | API 为 TypeScript 场景描述 + headless render API，确定性内置；但生态/Agent skills 远小于 HyperFrames，且引入自有 DSL 与 React 依赖 |
| 2 | **自建 Puppeteer + FFmpeg** | Puppeteer **Apache 2.0**（https://github.com/puppeteer/puppeteer/blob/main/LICENSE ，`Copyright 2017 Google Inc.`）；Playwright **Apache 2.0** | 免费 | 浏览器自动化本身极成熟（Puppeteer 2017 起 Google 维护、Playwright 2020 起 Microsoft 维护，均多年生产验证）；但**确定性逐帧渲染管线不成熟**——beginFrame warmup、`fonts.ready` 冻结规避、虚拟时钟、视频预解码、Docker 环境固定都要自己实现，详见 HeyGen 工程博客四大坑。仅在「完全不能有非 Apache/MIT 依赖」且愿意承担自研成本时选它 |
| 3 | **Remotion** | **自定义双轨许可，非 MIT/Apache**（https://www.remotion.dev/docs/license/pricing ，最后更新 2026-11-16） | 免费门槛原文：「individuals and companies of **up to 3 people**」；超出后：Automators `$0.01/render, $100/mo minimum`（agent/prompt-to-video/批量渲染落此档），Creators `$25/mo per seat`，Enterprise `starting at $500/mo` | 工程成熟、生态大，但**合规上反而比 HyperFrames 差**：本 MCP 是「Agent 自动生成 + 批量渲染」工具，正好命中 Automators 计费档（$100/月起），且 team 规模 >3 人即不再免费。只能作为 React 技术栈偏好者的工程备选，**不能作为合规备选** |

**关于 `$1M revenue/funding` 阈值**：第三方镜像站（remotionlab.com）声称免费门槛是「年收入 < $1M 且融资 < $1M」，但**官方 pricing 页（2026-11-16 更新）全文没有出现 revenue、funding 或 $1M 字样**，只有「up to 3 people」。以官方页为准，第三方说法标记为**未证实，不得据此做合规决策**（若需逐字确认，需查其 License FAQ / 资格检查工具，本次未找到）。

**结论不变**：HyperFrames 开源 CLI 真实可用，且「Agent 原生 + Apache 2.0 + 确定性 + headless + frame-accurate」五项同时满足，未发现更优替代。`WAR_MAP` 决策 #1 的后端选择继续执行，仅修正「Remotion 因合规而作备选」这一理由。
